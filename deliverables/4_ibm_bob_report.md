# تقرير توظيف IBM Bob في تطوير مشروع نظام تقييم المقررات الجامعية

---

## مقدمة

يُقدّم هذا التقرير توثيقًا شاملًا لكيفية الاستعانة بأداة **IBM Bob** (مساعد الذكاء الاصطناعي المدمج في بيئة التطوير) خلال مراحل بناء مشروع **نظام تقييم المقررات الجامعية**، مع إبراز القرارات التي اعتمدت على **التقييم البشري**، والمبادئ التي وجّهت استخدام الذكاء الاصطناعي بصورة مسؤولة.

---

## 1. دور IBM Bob في مراحل التطوير

### المرحلة الأولى — التخطيط والتصميم المعماري

**ما قدّمه Bob:**
- اقترح هيكل المشروع الكامل (App Router، مجلدات `lib/`، `components/`، `app/api/`)
- صاغ خطة تطوير مفصّلة من 10 مهام فرعية مرتّبة في ملف `university-course-eval-plan.md`
- رسم الحدود المعمارية الواضحة بين طبقة الواجهة الأمامية وطبقة API والقاعدة

**التقييم البشري المضاف:**
- قرار استخدام **TypeScript** بدلًا من JavaScript جاء بتوجيه صريح من المطوّر، وليس افتراضًا من Bob
- قرار الاعتماد على **create-next-app + Tailwind CSS** بدلًا من إعداد يدوي جاء باختيار بشري واعٍ بعد عرض الخيارين
- تحديد أن **الفصل الدراسي (semester) يُؤخذ تلقائيًا من المقرر المختار** وليس بإدخال الطالب له — قرار UX بشري لتبسيط تجربة الطالب

---

### المرحلة الثانية — بناء الـ Backend (API Routes)

**ما قدّمه Bob:**
- كتب الكود الكامل للمسارات الثلاثة:
  - `GET /api/courses`
  - `POST /api/evaluations`
  - `GET /api/evaluations/summary`
- تعامل مع حالة الخطأ `23505` (انتهاك القيد الفريد في Postgres) بإرجاع استجابة `409 Conflict`
- عزل `@supabase/supabase-js` في ملف `lib/supabase.ts` بحيث لا يصل إلى المتصفح أبدًا

**التقييم البشري المضاف:**
- مراجعة كود التحقق من صحة البيانات (validation) في مسار `POST /api/evaluations` والتأكد من شمولية الحالات
- التحقق من أن متغيرات البيئة الحساسة (`SUPABASE_URL`، `SUPABASE_ANON_KEY`) **لا تحمل بادئة `NEXT_PUBLIC_`** وبالتالي لا تُكشف للعميل — قرار أمني بشري صريح

---

### المرحلة الثالثة — بناء الواجهة الأمامية (Frontend)

**ما قدّمه Bob:**
- بنى مكوّنات React المعاد استخدامها: `StarRating`، `CourseCard`، `Navbar`
- صمّم صفحة الطالب (`/evaluate`) بمنطق التعامل مع الحالات الثلاث: نجاح / خطأ / تكرار
- بنى لوحة الإدارة (`/dashboard`) كـ Server Component تجلب البيانات عند كل طلب
- طبّق نظام ألوان أزرق وأبيض احترافي عبر Tailwind CSS

**التقييم البشري المضاف:**
- طلب صريح بأن **تظهر نجوم التقييم تفاعلية** (hover + selected states) وليست مجرد حقل رقمي — متطلب تجربة مستخدم بشري
- طلب تصنيف البطاقات من الأعلى تقييمًا إلى الأدنى — قرار عرض بشري
- توجيه بعدم إضافة نظام مصادقة (Auth) رغم أن Bob اقترح إمكانية ذلك — قرار نطاق (scope) بشري مقصود

---

### المرحلة الرابعة — الإعداد والنشر

**ما قدّمه Bob:**
- نفّذ `create-next-app` وتعامل مع مشكلة الاسم (الأحرف الكبيرة في مسار المجلد)
- ثبّت الاعتماديات وتحقق من نجاح `npm run build`
- هيّأ مستودع Git وكتب رسالة الـ commit الأولى

**التقييم البشري المضاف:**
- التحقق البشري من أن `.env.local` مُدرج في `.gitignore` قبل أي push
- قرار دفع الكود إلى GitHub يدويًا بعد إنشاء المستودع — إجراء أمني بشري (Bob لا يملك صلاحيات GitHub)

## 2. أبرز القرارات التي استندت إلى التقييم البشري

| القرار | السبب البشري |
|---|---|
| TypeScript بوضع strict | معيار جودة مختار للمشروع الجامعي |
| عدم إضافة نظام Auth | قرار نطاق مقصود لتوفير الوقت |
| عزل Supabase على السيرفر فقط | قرار أمني لحماية بيانات الاعتماد |
| الفصل الدراسي يُؤخذ من المقرر تلقائيًا | تبسيط تجربة الطالب |
| التحقق من `.gitignore` قبل الـ push | حماية بيانات الاعتماد الحساسة |
| تصنيف البطاقات من الأعلى إلى الأدنى | قرار عرض يخدم المسؤول الإداري |

## 3. مبادئ الذكاء الاصطناعي المسؤول (Responsible AI)

### أ) الشفافية (Transparency)

استُخدم IBM Bob كأداة مساعدة موثّقة بشكل صريح؛ جميع مخرجاته قابلة للمراجعة في ملف `university-course-eval-plan.md` وفي سجل المحادثة. لا يوجد كود "مخفي" أو منطق غير موثّق.

### ب) الرقابة البشرية (Human Oversight)

في كل مرحلة، راجع المطوّر الكود الناتج قبل تثبيته، وتحقق من صحة القرارات المعمارية، واحتفظ بسلطة الموافقة على كل ملف قبل إدراجه في المشروع. Bob لم يُنفّذ أي إجراء نهائي (كالـ push إلى GitHub) دون موافقة صريحة.

### ج) حماية البيانات والخصوصية (Privacy & Data Protection)

- بيانات الاعتماد (Supabase URL وKey) **لم تظهر في أي ملف مُرتكز** ولم تُدرج في Git
- Bob نبّه صراحةً إلى خطورة استخدام بادئة `NEXT_PUBLIC_` لمتغيرات السيرفر
- تقييمات الطلاب مرتبطة برقم هوية نصي فقط، دون بيانات شخصية حساسة

### د) محدودية النظام والإقرار بها (Limitations & Honesty)

Bob أقرّ صراحةً بأن:
- التجميع (aggregation) في JavaScript مناسب لهذا الحجم، لكن قاعدة بيانات PostgreSQL View ستكون أفضل للنطاق الأكبر
- النظام لا يحتوي على Auth حقيقي وهذا قرار مقصود وليس إغفالًا

### هـ) الحد الأدنى من التدخل (Minimal Footprint)

التزم Bob بمبدأ "أقل تغيير يحل المشكلة"؛ لم يُضف features غير مطلوبة، ولم يُعيد هيكلة أجزاء من الكود لم تكن جزءًا من المتطلبات.

## 4. الخلاصة

أسهم IBM Bob في تسريع دورة التطوير بشكل ملحوظ — من الصفر إلى تطبيق متكامل يجتاز `npm run build` بدون أخطاء — مع الحفاظ على دور المطوّر البشري كمرجع نهائي لكل قرار تقني وأمني وتجريبي. التوازن بين أتمتة الكود المتكرر والإشراف البشري على القرارات ذات الأثر هو جوهر التوظيف المسؤول لأدوات الذكاء الاصطناعي في مشاريع البرمجيات.
